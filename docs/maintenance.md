# 安装器维护与恢复

本页面向维护者，说明构建、验证、恢复和材料管理。用户操作见 [README](../README.md)，现场事实和已知问题见[验收报告](installer_report.md)，来源与许可见[来源与边界](source_and_evidence.md)。

## 固定构建与补丁

适用环境由[运行身份合同](../metadata/runtime_profile.json)限定：fnOS 1.2.0800、GRID P4-4Q、R535 535.309.01，以及 13 项保护文件、50 项外部依赖。Python 3.11+ 使用标准库；驱动、许可和 Docker 由已有宿主环境提供。

fnOS 1.2.0800 已完成本轮有限播放、同一开机恢复、工具安装及服务启动检查，详见[验收报告](installer_report.md#安装重启与恢复证据)。整机重启及其他格式未复测，不能继承旧版通过标记。v0.1.1 标签保留原 1.2.0701 合同，不改标签或 Release。

永久启用同时检查当前运行合同与安装／服务启动验收条件。未完成时只接受已绑定合同、机器、开机和有效期的试用；启动检查拒绝后清空自有注入，保留恢复材料，状态明确显示未验收。整机重启验收单独记录。

公开构建只读取仓库、[固定公开来源](../build/build_sources.json)和[286 项依赖版本](../build/build_packages.txt)。宿主负责下载及大小、SHA256、签名校验；依赖准备与两次干净编译在本地 Docker 中完成。两次输出都须匹配固定候选，身份不符时停止，不修改合同放行。

| 补丁 | 职责 | 应用顺序 |
| --- | --- | --- |
| [ac4_decoder.patch](../patches/ac4_decoder.patch) | 增加 AC4 decoder/parser 实现及注册，保留上游声明 | 第一步 |
| [ac4_parser_type.patch](../patches/ac4_parser_type.patch) | 将 parser 声明由 AVCodecParser 修正为 FFCodecParser，缺少会阻断构建 | 第二步 |

NVENC API 12.1 兼容由固定头文件和构建配置实现。两份补丁均属于当前构建输入，不能与已退役的 AC4 demux 实验混淆。补丁身份和顺序保持固定。

`build/` 保存构建脚本、固定来源和依赖清单，`builds/` 保存被忽略的构建结果，两者按职责分开。公开构建不读取旧私人镜像、试验归档或验收素材；nonfree 库与构建镜像仅本地保存。

## 本地验证

在既有 Linux 源码工作目录执行：

```bash
python3 -B -m unittest discover -s tests -p 'test_nvenc_*.py'
bash -n fnos-nvenc.sh
bash fnos-nvenc.sh --help
```

测试覆盖现行安装、运行控制、消费者与文件保护逻辑，服务和 GPU 使用替身。卸载消费者核对由 `nvenc_install.py` 执行，运行进程和库映射核对由 `nvenc_runtime.py` 执行。

`verify_materials.py` 只读核对维护者本地清单中的源码、基线库和必要记录，不属于公开克隆的安装前提。旧媒体实验及 SSH/FIFO 检查器不再提供。

| 证据层 | 能证明的内容 | 不能替代的内容 |
| --- | --- | --- |
| 解析与静态检查 | 语法和受检查规则 | 构建或现场运行 |
| 隔离软件测试 | 文件事务、恢复和拒绝行为 | 真实 systemd、GPU 或 NAS |
| 干净构建与哈希 | 输入、输出及候选身份 | 原生服务实际加载 |
| 服务／GPU 子进程映射 | 当次进程加载的实际库 | 人工音画体验、硬件解码或长期稳定性 |
| 有限播放与人工确认 | 本次素材、跳转及可接受体验 | 全格式、并发或长期验收 |

仅修改说明时检查 Markdown、载荷完整性、固定材料和最终 diff；不因此重跑构建或 NAS 验收。

## 现场变更与恢复

每次涉及服务变更，先确认当次授权、维护窗口以及所有播放和转码均已退出，包括直接播放。核对工具与候选身份，并保存本次开机的实际基线。

工具使用 root 所有版本目录、SHA256 清单和普通 JSON 原子指针。更新保留上一版与失败材料；启动钩子和安装器通过事务阶段、锁交接避免互相等待。

每次服务启动前先清空本工具注入，再核对组件并保存本次开机恢复点，最后写 `/run` 环境文件。启动准备与实际加载分开记录，旧开机状态不能用于新开机恢复。

暂停与卸载先恢复本次基线，再核对实际库、环境和配置。身份变化时只撤销归属明确的自有配置，保持“恢复未验证”；文件改动、恢复未闭合或消费者不明时停止删除。未知组合不会自动重启。

应用 GPU 开关、首选设备、启动准备、实际库映射和真实 GPU 子进程分别检查。设备明确选择 Tesla P4；变更首选设备后重新开始播放，并取得本次声音确认。

## 源码更新与工具恢复

| 源码布局 | 更新方式 |
| --- | --- |
| 普通 Git 克隆 | 在真实 Git 根执行 `git pull --ff-only`；若要更新已安装工具，先暂停补丁，再选 **3**。完整工具更新步骤见 [README](../README.md#更新与修复) |
| 已有 `source/` 等嵌套克隆 | 沿用真实 Git 根和原入口，不覆盖、不自动迁移 |
| 没有 `.git` 的发行快照 | 核对原提交与文件身份，另行准备完整新源码；不执行 `git pull`，不覆盖现有恢复材料 |

现场源码已于 2026-10-13 修复为真实 Git 克隆，根入口为 `/vol1/1000/Solis_FnOS_NVENC/fnos-nvenc.sh`。仅更新源码不会切换已安装工具；最后核对的提交、恢复副本和运行边界见[验收报告](installer_report.md#现场保留状态)。

1.2.0800 的源码与已安装工具分别更新。Git 源码同步到本轮适配后，根入口会读取新兼容清单；仅 `git pull --ff-only` 不重装工具、不重启服务、不换库。实际安装版本仍以 `/opt/solis-fnos-nvenc/tool/runner.sh status` 的结果为准。

当前工具损坏、上一版完整且补丁已暂停时，从保留源码目录运行：

保留源码须包含对应版本的兼容清单；尚未同步的旧源码可能拒绝升级后的组件。本次接入包的 `verified-input/` 也保留作修复输入，位置见[验收报告](installer_report.md#现场保留状态)。恢复旧工具指针只回退工具文件，不代表当前系统可以按旧清单启用补丁。

```bash
sudo bash fnos-nvenc.sh restore-tool
```

该动作验证上一版后切换工具指针，保留损坏文件。日常进入已安装工具使用：

```bash
sudo bash /opt/solis-fnos-nvenc/tool/runner.sh
```

核对已安装载荷时，使用它对应的源码提交和原清单。后续 `main` 文档更新不能用于判定旧安装已损坏，也不要求直接覆写 NAS 的清单文件。

现行源码将机器元数据放在 `metadata/`，构建输入放在 `build/`。安装载荷沿用相同布局；已安装旧版本继续使用自身的原清单，不迁移其文件。`nvenc_install.py` 中的 `docs/runtime_profile.json` 是旧工具识别所需的固定路径，保留用于验证和备份旧工具。

## 目录与材料管理

本项目是原生 mediasrv 辅助工具，下列路径是本项目明确的目录约定，不推广为其他项目规范。

`/opt/solis-fnos-nvenc/tool` 由安装器创建，每个版本按清单管理；菜单 **7** 先撤销补丁并核对恢复，**8** 再移除清单内身份匹配、无消费者的工具及已登记兼容库。恢复记录、旧工具备份和未登记材料不会一并清空，现有卸载不等于清除所有遗留文件。

已确认的下一包方向（尚未实现）：路径不迁移，在项目菜单统一列出全部自建材料的位置、用途和占用，并提供卸载后的残留清理预览。清理保留正在使用的版本、上一版和必要恢复点；未知来源、改动过的文件或有消费者的材料停止清理。该方向不授权当前删除或迁移。

| 位置 | 内容 | 保留／回收条件 |
| --- | --- | --- |
| `/vol1/1000/Solis_FnOS_NVENC/` | 源码、菜单与生成材料根 | 保留入口及恢复需要的来源，不覆盖已有目录 |
| 项目 `docs/` | 中文说明与配图 | 保留现行说明、必要结论和合同引用的证据 |
| 项目 `metadata/` | 当前运行身份、安装／启动验收标记、材料清单和必要旧检查 | 固定机器元数据，不作为临时文件清理 |
| 项目 `build/` | 构建脚本、来源合同和依赖版本清单 | 随源码保留，不与构建输出混用 |
| 项目 `builds/` | 构建输出，Git 忽略 | 所需候选、身份与恢复材料独立保留后，逐项判断 |
| 项目 `tmp/` | 安装输入副本、源码修复的恢复副本或当次暂存，Git 忽略 | 无消费者、无恢复依赖、身份完整且获当次授权后回收 |
| `/opt/solis-fnos-nvenc/` | 已安装工具版本和兼容库 | 仅由卸载流程移除身份匹配、无消费者的自建文件 |
| `/var/lib/solis-fnos-nvenc/` | 按开机区分的事务和恢复记录 | 默认保留，不作为普通临时文件清理 |
| `/run/` | 启动环境与临时运行状态 | 只属于当前开机，不重放历史状态 |
| 维护者本地 `artifacts/` | 四项源码缓存、当前库及身份文件、基线库，共七项固定材料 | 公开克隆无需预置；保留仍用于构建核验和恢复的材料 |
| 获批验收素材目录 | 自生成片源、配方与匹配字幕，Git 忽略 | 不属于安装载荷或恢复依赖；另行判断是否仍需使用 |

`tmp/install-input-*` 是安装／更新时生成的独立输入副本，包含源码载荷、候选库和身份文件。成功后仍保留，重复操作会累积；已安装工具从 `/opt` 运行，不从这些副本加载。`tmp/` 不存在不影响现有工具，后续安装可能重新创建。

本次源码修复的原快照保存在 `tmp/source_snapshot_before_git/`，`tmp/source_git_repair.json` 记录原提交、恢复位置和本次开机。两者用于源码目录还原，不是运行恢复合同，也不属于安装载荷；未经后续回收授权保留。

清理前逐项核对真实路径、内容变化、消费者、恢复引用以及符号链接／ReparsePoint。必要材料验证通过并取得当次清理授权后，NAS 使用 fnOS 文件管理器“移至回收站”，本地使用 Windows 回收站；不永久删除或清空回收站。

需要还原时，在 NAS 回收站按 `我的文件/Solis_FnOS_NVENC/tmp` 查找并选择“还原”；本地按原项目路径查找。已完成回收的结果见验收报告，不为过程另建审计 ZIP、历史目录或重复包。构建、旧版本和恢复记录没有自动清理任务。

## 有限播放验收

验收前重新确认测试窗口及当次恢复点。自生成测试素材保存实际编码、位深、色彩属性、配方与 SHA256；放入用户选定的既有媒体库子目录，不覆盖影片或修改媒体库设置。

每例明确记录片源、输出尺寸、一次跳转、真实 GPU 子进程、实际库和新的人工音画确认。外挂字幕明确选择本片条目；客户端 DOM／画布显示与服务端烧录分别判定。

字幕条目无效或自动选择报错时保留现象和未知根因，不自动删除条目或修复索引。7 天日常观察由用户进行，依据实际观察形成结论，不用短测结果代替。范围和待完成项统一保存在[验收报告](installer_report.md#已知问题与待完成验收)。

## 日志与许可

动作结果显示在终端，启动消息由 systemd 接收。近期服务消息可读取：

```bash
journalctl -u mediasrv.service -n 100 --no-pager
```

排障分享必要摘要，不公开私人原始日志、凭据或影片。本工具不修改系统日志轮转，也不自动回收构建和恢复空间。

## 中文文档维护约定

项目已绑定 Swift Cycle，沿用现有文档职责：[蓝图](blueprint.md)维护意图，[README](../README.md)提供用户入口，[DESIGN](../DESIGN.md)提供架构与导航，本页维护操作，验收报告保存验证事实。信息架构参考 [Diátaxis](https://diataxis.fr/)，中文表达参考[中文技术文档写作规范](https://github.com/ruanyf/document-style-guide)。

1. 一篇文档优先回答一类读者问题；同一事实只维护一个正文来源，其他页面提供简短说明和链接。
2. 标题说明内容或任务，正文先写结论。用户步骤写清前提、操作、预期结果和失败出口，避免命令流水账。
3. 使用简体中文和中文标点；中文与英文、数字之间统一留空格。路径、命令、JSON 字段、技术标识和第三方许可证保持原文。
4. 原则上使用三级以内标题。代码块标注语言，表格用于比较、映射或速查；长段拆分，链接使用能说明目的的标题。
5. 验证结论注明日期、版本、范围和证据层。状态统一使用“通过（PASS）”“有限通过（PASS）”“失败（FAIL）”“未验证（NOT_VERIFIED）”“未知（UNKNOWN）”；旧报告不当作实时状态。
6. 固定合同保留内容身份，其引用的完成报告保留路径和证据正文；获批目录整理须同步读取入口与链接。安装载荷中的快速说明可以维护，但不直接改写已安装版本。
7. 交付前审查最终 diff，核对 Markdown 链接及锚点、非空内容、代码块、安装载荷、固定材料和本地记录忽略状态，并运行 `git diff --check`。

后续若加入自动格式检查，可使用 [markdownlint-cli2](https://github.com/DavidAnson/markdownlint-cli2)，按上述约定选择规则。它检查 Markdown 格式，技术事实、授权、许可和验证边界仍须人工审查。现阶段沿用 Markdown 文件，不为文档新增站点或运行依赖。
